§ 1

O que está acontecendo (e por que não é culpa de vocês)

Na Aula 8 cada grupo construiu um MVP no Antigravity, com vários arquivos: index.html, dezenas de .ts, scripts Python, package.json, build do Vite e deploy pelo GitHub Actions. Funciona — mas é um projeto grande e dependente de ferramentas: precisa de Node, de Python, de terminal e de um agente que lê muitos arquivos a cada tarefa.

O resultado vocês viram: o agente carrega o repositório inteiro no contexto, lê e reescreve vários arquivos, entra em ciclos de correção — e os tokens acabam. Quando acabam, o agente fica lento, erra mais, "esquece" o que já foi feito e, em alguns casos, quebra o que estava funcionando.

O sintoma clássicoVocê pede um ajuste pequeno, o agente reescreve três arquivos, dois param de compilar, você pede para corrigir, ele reescreve outros quatro... e o saldo de tokens do dia acabou sem o problema resolvido. Não é incompetência sua nem do agente: é o formato do projeto.
A saída deste cadernoTransformar (ou reconstruir) o projeto em um único arquivo HTML — HTML, CSS, JavaScript e dados no mesmo index.html. Esse arquivo abre com duplo clique, não precisa de build e cabe inteiro numa conversa de ChatGPT, Gemini, Qwen, Claude, DeepSeek ou Copilot. Você passa a continuar o projeto de qualquer lugar, sem gastar tokens de agente.

Como usar este caderno

O caderno tem três trilhas. Use a que serve ao seu momento:

🏠

§ 4

Por que os tokens acabam no agente (e um HTML não gasta)

Um token é um pedaço de texto — mais ou menos 3/4 de uma palavra. Toda IA cobra (e limita) por tokens de entrada (o que você e o agente enviam) e de saída (o que ela responde). Um agente como o do Antigravity não trabalha com "um arquivo": a cada tarefa ele precisa ler vários arquivos do projeto para se orientar. Cada leitura, cada correção e cada nova tentativa reenvia contexto e consome tokens.

O que consome token no agentePor que é caroComo um HTML único muda isso
Ler o repositório a cada tarefaDezenas de arquivos .ts, .py, configs e node_modules entram na contaSó existe 1 arquivo para ler
Ciclo de correçãoCada tentativa reescreve arquivos e reenvia o contexto anteriorA IA devolve só o trecho alterado
Ferramentas e buildRodar npm, vite, pytest gera logs longos no contextoNão há build: o arquivo roda direto
Interdependência entre arquivosMudar um tipo quebra outros 3 arquivos, gerando novas rodadasTudo está no mesmo escopo, sem imports
Trocar de ferramentaO projeto só "vive" dentro do Antigravity com o ambiente certoO arquivo abre em qualquer navegador, em qualquer PC
A conta que importaEm um chat comum, um HTML de 60–150 KB ocupa poucos milhares de tokens. Um projeto Vite com node_modules não cabe numa conversa — por isso você não consegue simplesmente "continuar no ChatGPT". Com o arquivo único, você cola o projeto inteiro e conversa sobre ele.
§ 5

Por que um arquivo HTML resolve

Um único index.html autossuficiente reúne aplicação, estilo, lógica e dados. É a forma mais portátil de software que existe: qualquer navegador abre, sem instalar nada.

📦
1 arquivo só
🧩
Sem build/npm
💬
Cabe no chat
📶
Abre offline
🚀
Publica no Pages

O que você ganha

  • Continuidade: cola o arquivo em qualquer chat e segue de onde parou.
  • Portabilidade: abre com duplo clique no Windows, Mac, Linux ou celular.
  • Zero instalação: sem Node, sem Python, sem Vite, sem terminal.
  • Publicação fácil: um arquivo = um commit no GitHub Pages.
  • Contexto barato: menos tokens por conversa, respostas mais focadas.

O que você abre mão

  • Tipos do TypeScript (é JavaScript puro) — o cuidado com erros passa a ser seu.
  • Módulos e imports: tudo vive num só escopo (use nomes claros e funções).
  • Testes automatizados (Vitest/pytest) — a verificação passa a ser manual, no navegador.
  • O agente não "age" sozinho: você descreve e copia o resultado (o que é bom para economizar).
Um arquivo pode ser grande — e isso é esperadoÉ normal o HTML único ter 40, 80 ou 150 KB. O limite a respeitar é o da conversa: se ficar difícil colar inteiro, você divide a conversa em "colar o arquivo" e "pedir o trecho" (a Parte 2 ensina como).
§ 6

O que é (e o que não é) um HTML monólito saudável

"Monólito" não significa código bagunçado. Significa um artefato só, organizado por dentro. Siga as regras abaixo para que a IA consiga editá-lo sem quebrar o resto.

Regra do monólitoCertoErrado
Um arquivoindex.html com tudo dentroindex.html + app.js + style.css
EstiloCSS dentro de <style>Arquivo .css externo ou framework via CDN
LógicaJavaScript dentro de <script>Imports de módulos, bundler, TypeScript
DadosObjeto const DATA = {...} embutidofetch('dados.json') de arquivo separado
NavegaçãoRoteamento por hash: #/painelRotas /painel (quebram no Pages)
DependênciasNenhuma (JS e CSS puros do navegador)Bibliotecas externas por CDN (dependem de internet)
Recursos de appManifesto e service worker gerados no próprio arquivoConfiguração de Vite/PWA separada
Armadilha: voltar ao CDNA IA pode tentar "facilitar" colando <script src="https://..."> de uma biblioteca (Chart.js, Bootstrap...). Peça para não usar dependências externas: com internet instável ou offline, o app deve continuar funcionando. Gráficos podem ser feitos com SVG e canvas nativos.

§ 8

De vários arquivos para um: a arquitetura-alvo

Você não precisa apagar o projeto antigo — só criar um novo, menor, que é a versão que continua. Compare a árvore do que vocês fizeram na Aula 8 com a árvore do que vamos construir.

Como está hoje (Vite + TypeScript + Python)

  • mvp-pedidos-compra/
  • ├── package.json
  • ├── vite.config.ts
  • ├── tsconfig.json
  • ├── index.html
  • ├── src/
  • │ ├── domain/tipos.ts, regras.ts, kpis.ts
  • │ ├── pages/painel.ts, pedidos.ts
  • │ └── components/kpiCard.ts
  • ├── scripts/gerar_dados.py
  • ├── public/data/*.json
  • ├── tests/ (vitest + pytest)
  • └── node_modules/ ← milhares de arquivos

Como vai ficar (HTML único)

  • meu-projeto/
  • ├── index.html ← o aplicativo inteiro: HTML + CSS + JS + dados (const DATA)
  • ├── PROJETO.md ← o dossiê que abre qualquer chat de IA
  • ├── ESTADO.md ← o que já funciona e o que falta (a memória entre conversas)
  • └── README.md ← a apresentação para quem visitar o GitHub
Por que manter o PROJETO.md e o ESTADO.md separadosA IA não guarda memória entre conversas. Esses dois arquivos são a memória do projeto: um explica o que é o projeto, o outro registra onde ele está. Colar os dois no início de cada chat novo é o que impede a IA de recomeçar do zero ou inventar coisas.

§ 9

O PROJETO.md — o dossiê que abre qualquer conversa

O PROJETO.md é uma página única que resume o que é o projeto. Você cola ele no começo de toda conversa nova. Ele evita a pergunta que mais gasta tokens: explicar tudo de novo.

Modelo (o Laboratório A gera este arquivo a partir do seu contexto.md e sprint.md):

  • # PROJETO.md — [NOME DO PROJETO]
  • ## 1. Problema (a dor)
  • [o que dói hoje, para quem, com um número real ou estimado]
  • ## 2. Objetivo do MVP
  • [o que o sistema faz, em 2 frases. E o que ele NÃO faz.]
  • ## 3. Usuários e papéis
  • - [papel 1] — [o que pode ver/fazer]
  • - [papel 2] — [o que pode ver/fazer]
  • ## 4. Dados
  • [entidades e colunas; de onde vêm; tudo SINTÉTICO — nunca dado real]
  • ## 5. Regras de negócio
  • - RN01: [regra]
  • - RN02: [regra]
  • ## 6. Telas
  • - #/painel — [o que mostra]
  • - #/lista — [o que mostra]
  • ## 7. KPIs
  • - [nome] = [fórmula em uma linha]
  • ## 8. Stack
  • HTML único (CSS e JS inline), dados em JSON embutido (const DATA), publicado no GitHub Pages.
  • ## 9. Restrições e LGPD
  • Sem dados reais; sem dependências externas; acessível; funciona offline.
Mantenha curtoUm bom PROJETO.md tem entre 30 e 60 linhas. Se passar disso, a IA perde o foco. Detalhe fica no ESTADO.md e no próprio código.
§ 10

O ESTADO.md — a memória entre conversas

Se o PROJETO.md diz o que é, o ESTADO.md diz onde está. Atualize-o no fim de cada sessão (ou peça para a IA atualizar). Ele é o que permite abrir um chat novo e continuar exatamente do ponto certo.

  • # ESTADO.md — [NOME DO PROJETO] · atualizado em [DATA]
  • ## Já funciona
  • - [x] Tela #/painel com os 4 KPIs
  • - [x] Exportar CSV
  • - [x] Modo escuro
  • ## Falta
  • - [ ] Tela #/lista com filtro por unidade
  • - [ ] Gráfico de evolução mensal
  • ## Decisões tomadas
  • - Dados sintéticos com 200 registros (semente fixa).
  • - Sem bibliotecas externas; gráfico em SVG.
  • ## Próximo passo (só um)
  • - Implementar o filtro por unidade na tela #/lista.
Regra de ouro da continuidadeToda conversa nova começa com: PROJETO.md + ESTADO.md + o index.html atual. Toda conversa termina com: "atualize o ESTADO.md". Se você fizer só isso, nunca mais "perde" o projeto ao trocar de ferramenta.
§ 11

Como mandar o código para a IA sem estourar a conversa

Colar o arquivo inteiro a cada mensagem é o segundo maior gasto de tokens (o primeiro é o agente). Siga estas quatro práticas:

Ao COMEÇAR ou CONTINUAR

  • Cole PROJETO.md + ESTADO.md uma vez por conversa.
  • Anexe ou cole o index.html inteiro, uma vez.
  • Peça à IA para confirmar que entendeu antes de gerar código.

Ao PEDIR uma mudança

  • Peça só o trecho a alterar: "entregue apenas a função X".
  • Diga o que não pode mudar: "não altere as outras telas".
  • Uma tarefa por mensagem. Junte pedidos só quando forem triviais.

Quando a IA responde

  • Prefira diff/trecho a arquivo inteiro: "mostre só o bloco alterado".
  • Se ela reescrever demais, responda: "não repita o arquivo; mostre só a linha mudada".
  • Salve a resposta num arquivo de verdade e teste no navegador antes de pedir mais.

Quando o projeto cresce

  • Se o arquivo não couber com folga, divida em dois HTMLs (não em 10 arquivos).
  • Guarde versões: index-v1.html, index-v2.html.
  • Nunca edite o original sem ter uma cópia da última versão que funcionava.
§ 12

As 10 regras para render token (e não travar de novo)

  • Um objetivo por mensagem. Nunca peça "faz o sistema todo".
  • Sempre comece a conversa colando o PROJETO.md e o ESTADO.md.
  • Peça o arquivo completo só para criar ou reescrever do zero; fora disso, só o trecho.
  • Peça um plano antes do código quando a tarefa for grande.
  • Uma tela ou regra por vez — teste no navegador antes do próximo pedido.
  • Ao dar erro, cole o erro inteiro e diga o que você esperava que acontecesse.
  • Use duas IAs: uma constrói, a outra revisa (a segunda pega o que a primeira não viu).
  • Salve cada versão boa do index.html — o arquivo é a fonte da verdade, não o chat.
  • Atualize o ESTADO.md ao fim de cada sessão.
  • Não diga "deixa bonito"; diga exatamente o que mudar (tamanho, cor, ordem).
Se a resposta vier truncada"Continue de onde parou" costuma repetir conteúdo. Melhor: "pare de escrever no ponto X e continue a partir de Y, sem repetir o que já saiu". Ou peça o arquivo dividido em partes numeradas.
§ 13

A anatomia de um prompt de desenvolvimento que funciona

Prompt bom não é prompt grande — é prompt completo. Todo pedido de desenvolvimento deveria ter seis partes. Pule alguma e a IA preenche o vazio adivinhando (e adivinhar é onde nascem os bugs).

PeçaPergunta que ela respondeExemplo
PapelQuem deve me responder?"Atue como desenvolvedor front-end sênior."
ContextoO que você precisa saber do meu projeto?"Este é o PROJETO.md... o arquivo atual é..."
TarefaO que exatamente fazer?"Adicione o filtro por unidade na tela #/lista."
RestriçõesO que NÃO fazer?"Não altere as outras telas; sem bibliotecas externas."
FormatoComo entregar?"Mostre só a função alterada, em bloco de código."
Pronto quandoComo saber que acertou?"O filtro muda a tabela e o total, sem recarregar a página."
Quando
Sempre inclua o critério de pronto
Por que
Sem ele, a IA considera a tarefa terminada quando parece terminar — e você descobre o erro depois.
Exemplo no MVP
Ex.: "pronto quando eu clicar em 'Unidade: 1º BPM' e a tabela mostrar só os registros daquela unidade".

§ 14

Passo 0 — Decidir entre reconstruir e portar (e fazer backup)

Há dois caminhos, e a escolha depende do estado do seu projeto atual:

Reconstruir do zero (recomendado)

  • Quando o projeto está quebrado, incompleto ou você se perdeu no código.
  • Você usa o PROJETO.md como planta e gera um HTML único limpo.
  • Mais rápido e com menos bugs. A IA não precisa "entender" o código antigo.

Portar o que existe

  • Quando o projeto está funcionando e você só quer compactá-lo.
  • Você manda os arquivos-núcleo e pede a conversão para HTML único.
  • Guarda o comportamento atual, mas exige mais atenção da IA.
  1. Faça o backup
    Copie a pasta do projeto atual para nome-do-projeto-backup. Não mexa sem isso.
    Ctrl+C / Ctrl+V da pasta, renomeando.
  2. Crie a pasta nova
    Crie uma pasta separada só para o HTML único. É nela que você vai trabalhar daqui pra frente.
    Ex.: D:\SESP\meu-projeto.
  3. Escolha o caminho
    Se o projeto funciona bem, vá de portar; se está confuso, vá de reconstruir.
    Na dúvida, reconstruir.
Você não está jogando nada foraO projeto antigo continua no GitHub e no backup. O HTML único é a versão que será continuada — mais leve, que cabe no chat e publica igual no GitHub Pages.
§ 15

Lab A — Gerar o PROJETO.md e o ESTADO.md

§ 32

Glossário rápido

HTML único / monólito

HTML único
Um arquivo .html que contém aplicação, estilo, lógica e dados.
Inline
O CSS/JS vem dentro do próprio HTML (<style>/<script>), não em arquivos separados.
DATA
O objeto JavaScript com os dados embutidos no arquivo (const DATA = {...}).
Build
Processo de compilar/empacotar o projeto (Vite, npm). No HTML único, não existe.
CDN
Servidor externo que entrega bibliotecas; criar dependência dele. Evitamos.

Continuidade e publicação

PROJETO.md
Dossiê de uma página que explica o que é o projeto; cola-se no início de cada conversa.
ESTADO.md
Registro do que funciona e do que falta; a memória entre conversas.
Handoff
Passar o projeto para um chat novo sem perder contexto.
Roteamento por hash
Trocar de tela pelo endereço depois do # (#/painel); funciona em hospedagem estática.
GitHub Pages
Hospedagem gratuita de site estático a partir de um repositório.
PWA / service worker
Site instalável que funciona offline; gerado no próprio arquivo.
LGPD
Lei de proteção de dados: dado real de pessoa não vai para IA nem para repositório público.
